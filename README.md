# RMS — Restaurant Management System

Веб-система управления рестораном с модулем **поддержки принятия решений**:
она не только принимает заказы, но и сама подсказывает владельцу,
что рекламировать, где поднять цену, какое комбо предложить и когда усилить смену.

**Стек:** Go + Gin · PostgreSQL (pgx) · JWT + bcrypt · HTML/CSS/JavaScript (fetch, SVG-графики без библиотек) · Claude API (ИИ-ассистент)

## Запуск

Сначала настройки — пароли и ключи хранятся не в коде, а в `backend/.env` (он в `.gitignore`):

```bash
cd backend
cp .env.example .env
# впишите пароль PostgreSQL в DATABASE_URL и сгенерируйте секрет:
openssl rand -base64 48      # → значение для JWT_SECRET
cd ..
```

Переменные, заданные в окружении, важнее файла — на сервере их можно передать снаружи без `.env`.
Без `DATABASE_URL` или с `JWT_SECRET` короче 32 символов сервер не стартует и пишет, что исправить.

```bash
# 1. Миграция (себестоимость, проверки статусов и ролей, индексы)
psql "postgres://postgres:postgres@localhost:5432/restaurant_management" \
     -f backend/database/migrations/001_analytics.sql
# склад и техкарты
psql "postgres://postgres:postgres@localhost:5432/restaurant_management" \
     -f backend/database/migrations/002_inventory.sql

# 2. Демо-данные: меню, сотрудники, 250 клиентов, ~15 000 заказов за 180 дней,
#    37 продуктов, техкарты всех блюд и начальные остатки склада.
#    Повторный запуск заказы не дублирует; пересоздать: go run ./cmd/seed -reset
cd backend && go run ./cmd/seed

# 3. Сервер (API + фронтенд) → http://localhost:8080
go run ./cmd/server
```

Демо-сотрудники (пароль `password123`): `waiter@rms.kz`, `cook@rms.kz`, `owner@rms.kz`.

## Роли

| Роль | Что может |
|---|---|
| customer | меню, корзина, заказ, история, отмена заказа до подтверждения |
| waiter | очередь заказов: принять, отменить, выдать гостю |
| cook | очередь заказов, склад: приход поставок, инвентаризация |
| admin | всё: блюда, категории, заказы, аналитика, закупки, склад, ИИ-ассистент |
| owner | дашборд, аналитика, прогноз, закупки, ИИ-ассистент, просмотр склада |

Жизненный цикл заказа проверяется на сервере (`handlers/orders.go`):

```
pending → confirmed → preparing → ready → completed
   └────→ cancelled
```

## Модуль аналитики и поддержки решений

Все расчёты — в `backend/handlers/analytics.go`: агрегаты считает PostgreSQL,
правила классификации и рекомендаций написаны на Go.

| Анализ | Метод | Какое решение даёт |
|---|---|---|
| KPI | выручка, заказы, средний чек, валовая прибыль vs прошлый период | общая динамика |
| Инженерия меню | матрица Kasavana & Smith: популярность (порог 70% от 1/N) × маржа с порции (порог — средняя) → ⭐ звёзды, 🐴 лошадки, ❓ загадки, 🐶 собаки | что рекламировать, где поднять цену, что убрать |
| Анализ корзин | ассоциативные правила: support, confidence, lift | комбо-наборы, «с этим берут» на странице блюда |
| Нагрузка | средние заказы по дню недели × часу | график смен персонала |
| Прогноз спроса | Холт — Уинтерс (уровень + тренд + недельная сезонность), α β γ подбираются перебором по сетке; прогноз по дням и по каждому блюду | сколько заказов завтра и сколько порций готовить |
| Закупки | линейное программирование (симплекс-метод, `handlers/simplex.go`) по прогнозу, техкартам, остаткам и бюджету | что и сколько купить, какие блюда обеспечить при нехватке денег |
| Рекомендации | правила поверх всех анализов | список конкретных действий для владельца |

### Точность прогноза

Прогноз проверяется так же, как используется: 4 раза модель обучается только на
прошлом и прогнозирует следующую неделю (rolling origin), результат сравнивается с
наивным прогнозом «как в тот же день неделю назад».

| Модель | Ошибка (MAPE) |
|---|---|
| Наивный прогноз | 12,8% |
| Холт — Уинтерс | **11,1%** (на 13% точнее) |

Нижняя граница здесь — случайный шум: при ~65 заказах в день он сам даёт ~10% ошибки.
Код: `backend/handlers/forecast.go`.

### Оптимизация закупок

```
максимизировать   Σ цена_блюда·порции − Σ цена_продукта·закупка
при условиях      Σ техкарта·порции − закупка ≤ остаток   (для каждого продукта)
                  Σ цена_продукта·закупка     ≤ бюджет
                  порции                      ≤ прогноз·(1 + запас)
```

Решается собственным симплекс-методом (правило Бленда против зацикливания,
покрыт тестами `handlers/simplex_test.go`), дробные килограммы округляются до
упаковок в пределах бюджета. Кроме плана система показывает:

- **теневую цену бюджета** — сколько прибыли даёт ещё 1 ₸ (двойственная оценка);
- **кривую «бюджет → прибыль»** — та же задача для 0–100% бюджета, видна убывающая отдача;
- **какие блюда обеспечены** — при нехватке денег решатель сам отказывается от
  низкомаржинальных блюд (на демо-данных это «Наггетсы» и «Ролл с угрём» — те же «собаки»,
  что нашла инженерия меню).

Склад связан с кухней: когда повар начинает готовить заказ, продукты по техкартам
списываются со склада в той же транзакции, что и смена статуса.

### ИИ-ассистент владельца

Чат в панели («🤖 ИИ-ассистент»): владелец спрашивает обычными словами —
«что прорекламировать?», «что закупить на 300 000 ₸?», «напиши пост про самое выгодное блюдо» —
и получает ответ с цифрами и конкретным действием.

**Модель не считает сама.** Claude (модель `claude-opus-5`, официальный Go SDK, tool runner)
получает 7 инструментов, и каждый вызывает те же функции Go, что и страницы аналитики:
KPI, инженерия меню, прогноз, план закупок (симплекс), анализ корзин, загрузка по часам, рекомендации.
Поэтому любая цифра в ответе совпадает с графиками, а под ответом видно, из каких расчётов она взята.

Подключение — ключ Claude API (console.anthropic.com → API Keys) в `backend/.env`,
в коде и в git ключа нет:

```bash
ANTHROPIC_API_KEY=sk-ant-...
```

После этого перезапустите сервер.

Без ключа ассистент отвечает `503` с понятным сообщением, остальная система работает как обычно.
Код: `backend/handlers/assistant.go`, тесты инструментов на реальной базе: `assistant_test.go`.

### Проверка на заложенных закономерностях

Генератор (`backend/cmd/seed`) специально закладывает в данные закономерности,
а аналитика должна найти их сама, не зная о них:

| Заложено | Найдено системой |
|---|---|
| к бургеру берут фри в 65% случаев | confidence «Чизбургер → Картофель фри» ≈ 67% |
| к суши берут Мохито в 30% | «Филадельфия → Мохито» ≈ 34% |
| пики в обед и вечер, выходные ×1,4–1,55 | тепловая карта: Сб/Вс 13:00 и 19:00 |
| «Дракон» — дорогой и маржинальный, но редкий | класс ❓ «загадка» → рекомендация «прорекламировать» |
| «Чизбургер» — ходовой, но с низкой маржой | класс 🐴 «лошадка» → «поднять цену на ~10%» |

## Тесты

```bash
cd backend && go test ./...
```

| Пакет | Что проверяется |
|---|---|
| `app/api_test.go` | настоящие HTTP-запросы через тот же роутер, что у сервера: регистрация и вход (хеш bcrypt, одинаковая ошибка для неверного пароля и несуществующего email), отказ для просроченного, чужого, «alg: none» и мусорного токена; матрица доступа ролей (19 случаев); заказы — цена только из базы, объединение повторов, скрытое блюдо, чужой заказ = 404, отмена клиентом только до подтверждения, переходы статусов по ролям, списание продуктов по техкарте ровно в момент «Готовится» |
| `handlers/simplex_test.go` | симплекс-метод: учебный пример и двойственные оценки, неограниченная задача, вырожденный пример Била, теневая цена бюджета |
| `handlers/assistant_test.go` | все 7 инструментов ассистента на реальной базе, валидация запросов, режим без ключа |

Интеграционные тесты работают с локальной базой и после себя всё убирают:
созданные пользователи, заказы и блюда удаляются, остатки склада восстанавливаются.
Если PostgreSQL не запущен, они пропускаются.
